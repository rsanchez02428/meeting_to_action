SPEAKER IDENTIFICATION (CRITICAL — DO THIS BEFORE EXTRACTION):
Before extracting any content, make a first pass through the transcript 
to identify and label every distinct speaker. Follow these steps in order:
 
Step 1 — Detect turn boundaries.
  A new speaker is talking when you see shifts in stance: responses 
  ("I agree", "Understood", "Good", "Yes", "Exactly"), questions 
  answered by the previous statement, or a change in perspective 
  (reporting vs. directing, asking vs. answering).
 
Step 2 — Assign labels in order of first appearance.
  - The FIRST person to speak is "Participant 1".
  - The SECOND distinct person to speak is "Participant 2".
  - Continue numbering for any additional speakers.
 
Step 3 — Upgrade labels when names appear.
  If at any point a speaker is addressed by name (e.g., "Thanks, 
  Dian" or "Dian, can you…"), replace their Participant label 
  with their actual name for ALL occurrences — past and future.
  The speaker saying the name is NOT the named person; they are 
  addressing someone else.
 
Step 4 — Note roles from context.
  If a speaker's role is evident (e.g., they direct others, set 
  deadlines, or are called "boss" / "manager"), note this in the 
  participants list but still use the assigned label (name or 
  Participant N) for attribution throughout.
 
ATTRIBUTION RULES:
- Use the assigned label (name or Participant N) consistently 
  everywhere: action_items.owner, decisions.made_by, 
  open_questions.raised_by, and participants.
- NEVER default to the named person when uncertain. If you cannot 
  confidently attribute an action, mark it "Unassigned".
- When someone says "I'll do X", owner = that speaker's label.
- When someone says "You'll do X" to another, owner = the other 
  person's label.
 
THE RECAP RULE:
Many meetings end with an explicit action-item recap (signaled by 
phrases like "let's lock in the action items", "to summarize", "so 
to clarify…", numbered lists like "First… Second…"). 
 
When a recap exists, the recap is AUTHORITATIVE for:
  - Owner of each action item
  - Scope of each action item  
  - Deadline of each action item
 
If an earlier statement and the recap disagree, trust the recap. 
You should still extract action items mentioned only outside the 
recap, but the recap overrides earlier ambiguity.
 
ACTION ITEM GRANULARITY:
Extract action items at an ATOMIC level. Do NOT consolidate sub-tasks 
into parent tasks. If someone commits to a multi-step plan, extract 
each distinct executable step.
 
Example — if a speaker says: "I'll handle the client onboarding for 
Acme next week — I'll send the welcome packet on Monday, schedule 
the kickoff call with their three stakeholders, and have the shared 
workspace set up before the call so they can start uploading files."
 
This is FOUR action items, not one:
  1. Onboard Acme as a client next week (overall)
  2. Send the welcome packet on Monday (communication step)
  3. Schedule the kickoff call with three stakeholders (coordination step)
  4. Set up the shared workspace before the kickoff call (enablement step)
 
Rule of thumb: if a step has its own owner, deadline, or could be 
checked off independently, it is its own action item.
 
Commonly missed sub-types — pay attention to these:
  - Resourcing steps ("Free up five people from Team B to help")
  - Scoping steps ("Focus on the top ten accounts first")
  - Deliverable steps ("Send me the summary before the call")
  - Process-implementation steps that flow from a decision — if the 
    team decides "all orders require a second sign-off before 
    shipping," someone must implement that. Extract the action.
 
DECISIONS:
A "decision" is any point where direction is set or confirmed — not 
just a big strategic choice. Include ALL of the following:
 
  - Active choices ("We'll go with Vendor B")
  - Acceptances of constraints ("We'll have to share the conference 
    room with marketing until the renovation is done" — followed by 
    agreement like "Fine" or "Okay")
  - Process changes ("From now on, X requires Y")
  - Postponements ("We'll defer this until next quarter")
  - Removals/exclusions ("No new hires on client projects until 
    they finish onboarding")
  - Confirmations/affirmations — agreeing that something already in 
    place is correct or acceptable ("Are we still good with the 
    timeline?" + "Yes, we're on track" = decision that the timeline 
    stands)
  - Editorial/content agreements — one speaker proposes a specific 
    change to a document, message, or deliverable and the other 
    explicitly agrees ("I think we should soften the language in 
    section three" + "Agreed" = decision to revise the wording)
  - Timebound commitments — agreeing to a measurement window, trial 
    period, or evaluation timeline ("Let's run the pilot for two 
    weeks and then reassess" = decision on evaluation timeframe)
 
DECISION DETECTION PRINCIPLE:
If one speaker proposes something — no matter how small — and another 
speaker explicitly agrees ("Agreed", "Exactly", "Yeah that works", 
"Fine", "Good", "Okay", "That makes sense"), that exchange is a 
decision. Scale does not matter. A decision to adjust one paragraph is 
as much a decision as a decision to switch vendors.
 
If a decision also produces an action, list it in BOTH places — under 
decisions (the agreed direction) and under action_items (the 
executable form with owner and deadline).
 
DEADLINE PRESERVATION:
1. Preserve deadline wording EXACTLY as spoken. Do not normalize, 
   do not add AM/PM, do not convert relative dates to absolute dates.
   - Transcript says "by 930" → deadline is "by 9:30", not "9:30 AM"
   - Transcript says "EOD" → deadline is "EOD", not "by 5 PM today"
   - Transcript says "Friday" → deadline is "Friday", not a date
 
2. A deadline applies ONLY when explicitly tied to the action.
   Background facts about timing are NOT deadlines.
   - "The vendor says the parts will arrive by Thursday" describes 
     a vendor timeline, NOT a deadline for the person who said 
     "I'll follow up with the vendor to speed things up". That 
     action's deadline is "Not specified".
 
COMMITMENT vs. SUGGESTION:
- "I'll do X" / "I'll handle that" → action item, owner = speaker
- "Can someone look into X?" → action item, owner = "Unassigned"
- "Alex, you'll do X" → action item, owner = Alex
- "We should do X" with no commitment → open question, NOT action
- "We need to do X" followed by someone accepting → action item
- A statement of intent counts even if related work is already 
  underway elsewhere. "I'll push them" is still an action item even 
  if they are already working on the problem.
 
PRIORITY:
- "high" if words or tone are SIMILAR TO "urgent", "ASAP", "critical", 
  "blocker", "today", "immediately", "starting now" are used
- "medium" is the default
- "low" for nice-to-haves and future considerations

Respond with ONLY the JSON object. No markdown, no explanation, 
no code fences.
